# 작업 복구 2차: 중단 이어하기·실패 항목 재시도

상태: 사용자 승인 후 구현·검증 완료. 배포 1.0.1.10 (2026-10-11), 전체401개 회귀/399통과/2skip. 상세 증거는 docs/VALIDATION.md.

## 1. 목표와 범위

저장한 작업에서 미처리 파일을 이어서 정리하고, 실패한 단계만 다시 처리한다. 모델 선택·수동 파일명·SEQ·분류 경로·출력 설정은 실행 당시 값으로 고정한다. 성공 파일을 처음부터 다시 복사하거나 이동하지 않는다.

실행 중 정상 일시 정지, ffmpeg 내부 프레임부터 재개, 휴대폰 전송 이어하기, 사진 내용 해시 비교는 이번 범위에서 제외한다. 중단한 영상 인코딩은 안전한 항목에 한해 영상 한 개를 처음부터 다시 변환한다. 원본 촬영 날짜 추출과 모바일 복사 정책은 기존 기능을 유지한다.

완료 순서: 단계별 실행 기록 → 읽기 전용 복구 계획 → 검증된 단계 실행 → UI 및 구버전 호환 → 중단 지점 테스트/독립 검토 → 문서·4자리 버전·EXE 빌드.

## 2. 방식 비교와 권장안

| 방식 | 장점 | 한계 |
|---|---|---|
| 전체 ERROR 항목 재실행 | 구현이 작음 | main 성공 후 output 실패를 구분하지 못해 이미 만든 파일을 다시 처리함. 채택하지 않음 |
| 결과 없는 파일만 이어하기 | 변경 범위가 작음 | 실제 변경 후 결과 기록 전 종료된 파일은 여전히 판정 불가. 출력만 재시도 불가 |
| 단계별 실행 저널과 복구 계획 | 성공 단계 유지, 출력만 재시도, 불확실 항목 차단 | 저장 모델·엔진 변경과 중단 지점 검증 필요. 권장 |

## 3. 항목별 상태

기본 정리(main), 모바일 출력(output), 이동 원본 제거(source_remove)를 각각 기록한다. 공통 상태는 PENDING, IN_PROGRESS, DONE, FAILED, UNCERTAIN, NOT_REQUIRED다. output에는 SKIPPED, SIZE_EXCLUDED를 추가한다. 차단 사유는 기록된 과거 상태와 별도의 현재 검증 결과로 보관한다.

| 기록·현재 상태 | 복구 동작 |
|---|---|
| main PENDING, 원본 기준 일치, 최종 경로 없음 | 기존 이름·경로로 일반 정리 실행 |
| main DONE, 완료 당시 Target 기준 일치 | main 유지. 다시 복사·이동하지 않음 |
| main DONE, output FAILED, Target 기준 일치 | 검증된 Target을 입력으로 output만 재시도 |
| output SKIPPED / SIZE_EXCLUDED / NOT_REQUIRED | 정상적인 정책 종료로 유지. 재시도 제외 |
| 성공 기록의 파일 변경·누락 | 현재 확인 필요로 차단. 성공을 PENDING으로 되돌리지 않음 |
| 단계 IN_PROGRESS에서 종료, 완료 기록 없음 | UNCERTAIN으로 표시. 파일 존재·크기만으로 성공 또는 실패를 추정하지 않음 |
| 원본 변경·경로 이탈·링크·근거 없는 기존 최종 파일 | 해당 항목 차단. 파일 보존 |

FAILED는 모든 예외의 통합 표기가 아니다. 최종 변경을 시작하지 않았거나 변경 실패와 임시 파일 소유권을 확실히 확인한 실패만 재시도 후보가 된다. 최종 게시·원본 제거가 시작된 뒤 완료 기록을 남기지 못하면 UNCERTAIN이다.

main DONE 후 output 입력은 copy/move 모두 검증된 Target이다. move 원본이 없다는 사실만으로 실패로 판정하지 않는다. 새 저널 실행의 move는 Target 생성과 output의 정상 종료를 확인한 뒤 원본 제거를 마지막 단계로 수행한다. output 오류 시 원본을 보존하고 재개 후 마지막 단계를 마무리한다. 이 순서 변경은 구현 전 확인할 정책이다.

원본 제거 직전 main/output 완료 근거, 원본 고정 기준값, 링크 여부를 다시 검사한다. 원본 제거가 IN_PROGRESS로 남으면 자동 삭제하지 않는다. copy 작업의 원본 삭제는 기존 삭제 리뷰에서만 수행하며 복구가 자동으로 삭제 체크를 선택하지 않는다.

## 4. 저장 구조와 호환

새 작업 저장 형식은 schema_version=2로 한다. Qt와 분리한 단계 모델과 저널 저장 모듈을 추가한다. 외부 패키지 없이 Python 표준 sqlite3를 사용한다.

- 실시간 기준 저널: 실행 폴더의 sessions/execution_journal.sqlite. SQLite synchronous=FULL, 짧은 트랜잭션으로 단계 의도와 완료를 각각 저장한다. 복사·변환 중에는 DB 트랜잭션을 유지하지 않는다.
- JSON 작업 파일: 기존 *.pojob.json을 유지한다. 고정 계획과 내보내기 시점의 단계 기록을 포함한 휴대 가능한 스냅샷이다. 원자 저장·크기/목록 제한·엄격한 스키마 검증은 유지한다.
- 최근 복구 JSON: last_session.pojob.json을 유지한다. 실행 시작 전에 실행 ID와 계획을 저장하고, 시작 시 같은 계획의 최신 DB 단계 기록으로 화면을 구성한다. 단계마다 전체 10만 항목 JSON을 다시 쓰지 않는다.
- 전역 자동 저장를 꺼도 DB 실행 기록은 필수다. 시작 기록 실패는 실행을 막고, 실행 중 기록 실패는 다음 파일 변경을 막는다. 성공 후 최근 JSON 저장 실패가 이미 DB에 확정된 성공을 취소하지는 않는다.

job_id는 문서 ID, plan_id는 고정 미리보기 계획 ID, execution_id는 실행 ID다. 선택·수동명·경로·처리 설정을 변경해 계획을 갱신하면 plan_id를 새로 만든다. 다른 이름으로 저장은 job_id만 새로 만들고 plan_id/execution_id를 유지한다.

DB의 plan_id UNIQUE 등록으로 같은 미리보기의 중복 실행을 차단한다. execution_id가 없는 오래된 PREVIEW_READY 사본도 plan_id로 이미 시작한 실행을 확인한다. 단순히 ID가 같다는 이유로 기록을 합치지 않고 경로·설정·선택·원본 기준을 포함한 계획 전체 일치를 검사한다.

저널 이벤트는 단조 증가 순번을 갖는다. DB가 JSON보다 앞서 있으면 DB 이벤트를 JSON의 checkpoint 순번까지 재구성하여 내장 단계 상태 전체와 비교한다. 일치하는 과거 스냅샷은 정상적인 뒤처짐으로 보고 최신 DB를 적용한다. 동일 순번 상태 불일치, JSON이 DB보다 앞섬, 검사할 이력 누락은 충돌로 차단한다. 순번만 큰 기록을 무조건 채택하지 않는다.

JSON 내보내기는 DB의 단일 읽기 트랜잭션에서 일관된 스냅샷을 얻는다. 실행 저널이 없는 다른 폴더/PC에서는 내장 기록으로 화면과 결과만 복원하고 실행 시작 작업의 이어하기·재시도를 비활성화한다. 내보내기 이후의 진행을 알 수 없으므로 최신 완료 기록이라고 표시하지 않는다. 실행 폴더를 옮길 때는 sessions의 DB와 최근 복구 파일도 함께 보존해야 한다. DB 손상 시 임의로 빈 DB로 대체해 실행하지 않는다.

schema1의 미리보기는 기존 재검증 후 최초 실행 가능하고 그 실행부터 새 저널을 만든다. 변환할 plan_id는 고정 namespace와 정규화한 불변 계획 JSON으로 UUID5를 계산한다. 같은 구형 계획을 반복 열거나 이름만 바꿔도 같은 ID를 얻는다. 문서 ID/revision/저장 날짜/로그/전역 설정은 제외하고 선택·원본 기준·경로·파일명·처리 설정은 포함한다. 이는 미디어 내용 해시나 중복 이미지 비교가 아니다. 명시적으로 새 미리보기를 만들면 새 plan_id를 생성한다.

schema1에서 이미 실행한 작업은 결과 조회·모바일 복사·검증된 삭제 리뷰를 유지하되 자동 재개/재시도는 제공하지 않는다. 기존 ERROR에 main 성공 근거를 추정해서 추가하지 않는다. schema1 파일을 새 형식으로 저장해도 실행 증거가 새로 생기지는 않는다. 1.0.1.9는 schema2를 열 수 없다.

## 5. 파일 변경과 저장 순서

1. 실행 직전 같은 Windows PC의 새 버전 인스턴스에 공통인 Global PhotoOrganizer 실행 mutex를 확보한다. 실행 폴더·DB·문서 ID가 달라도 한 번에 미디어 실행 하나만 허용한다. OS가 종료 시 해제하는 잠금을 사용하고 PID 존재 여부만으로 잠금을 판단하지 않는다. 잠금 확보 후 현재 경로·원본·계획을 재검증한다. 다른 PC·구버전·외부 프로그램은 이 잠금에 참여하지 않으므로 게시 직전 충돌 검증도 유지한다.
2. execution 등록과 최근 복구 시작 기록을 디스크에 저장한다. 저장 실패 시 미디어를 수정하지 않는다.
3. 단계 시작 의도, item/attempt ID, 임시 경로와 최종 경로를 DB에 확정한다.
4. 해당 시도 소유의 임시 파일에 작업한다. NEW 파일과 복구의 최종 게시는 기존 파일을 덮어쓰지 않는 방식으로 수행한다. 임시 파일을 완성한 뒤 크기·메타데이터/촬영 날짜 적용 등 단계 검증을 마친다.
5. 최종 게시 전에 검증과 게시 의도를 저장한다. 게시 뒤 완료 파일 기준값을 기록하고 그 트랜잭션이 성공해야 다음 단계로 이동한다.
6. 파일 변경 성공 후 완료 저장이 실패하면 되돌렸다고 표시하지 않는다. 기존 파일을 보존하고 UNCERTAIN으로 중단한다.

최초 실행의 기존 OVERWRITE 정책은 이 기능이 임의로 확대하지 않는다. 기존 정책을 적용한 항목도 단계 의도/완료를 기록하되, 중단 후 기존 최종 파일을 다시 덮어쓰는 재개는 금지한다. 완료 근거가 없으면 확인 필요다. 복구에서 새 SEQ나 새 파일명을 자동 생성하지 않는다.

기존 ffmpeg의 고정 .tmp 파일을 복구 시도에 공유하지 않는다. 임시 경로는 execution/item/attempt로 유일하게 만들고 저널에 소유권을 기록한다. 실패 정리는 현재 시도가 생성한 것으로 확인된 임시 파일만 대상으로 하며 출처를 모르는 기존 파일이나 output_ 폴더 전체를 삭제하지 않는다. 끊긴 시도의 부분 임시 파일은 자동으로 성공 결과에 채택하지 않는다.

파일 게시와 DB 완료 기록은 하나의 원자 트랜잭션으로 묶을 수 없다. 이 사이에 종료되면 확인 필요 상태가 남는 것을 정상적인 안전 동작으로 정의한다. 크기·mtime는 변경 탐지용이며 내용 동일성/소유권 보증으로 사용하지 않는다.

## 6. 사용자 흐름

기존 일반 실행은 실행을 시작하지 않은 계획에서만 사용한다. 실행 결과 영역에 이어서 실행과 실패 항목 재시도를 추가한다. 정상 완료에는 두 버튼을 비활성화한다. 처리 종료는 성공 N / 오류 N / 미처리 N / 확인 필요 N으로 구분한다.

이어서 실행은 안전하게 확인한 미처리 단계만 대상으로 한다. 실패 항목 재시도는 재시도 가능한 FAILED 단계만 대상으로 한다. 완료 여부 미확인 단계는 두 동작에서 제외한다. 실행 전에 읽기 전용 복구 계획 창으로 완료 유지·미처리 실행·output만 재시도·이동 마무리·확인 필요와 사유를 보여준다. 사용자가 가능한 항목 실행을 누르면 잠금 획득 후 다시 검증한 계획만 수행한다.

차단 항목은 남겨 두고 가능한 항목만 처리할 수 있다. 재개에서 설정·이름·SEQ는 변경하지 않는다. 변경하려면 새 작업을 사용한다. 실행 중 전환/종료 차단은 유지한다. 실패한 영상은 통째로 다시 변환되며 내부 진행 위치 복원은 지원하지 않는다.

이전 시도 기록은 보존하고 최신 결과를 항목별로 표시한다. 삭제 후보는 안전하게 완료된 copy 항목별로 중복 없이 갱신하고 체크 해제한다. 모바일로 복사는 현재 Target의 실제 output_ 검색 흐름을 유지한다.

## 7. 구현 단위와 검증

1. 단계 모델/SQLite 저널/plan ID/스키마2 및 엄격한 스키마1 판독.
2. 읽기 전용 복구 계획과 상태 검증, 단계별 엔진 진입점. 일반 execute를 결과 전체에 재호출하지 않는다.
3. main/output 단계 기록·시도별 임시 파일·검증된 output 단독 재시도.
4. move의 마지막 원본 제거 단계와 삭제 리뷰 기준값 보존.
5. UI 복구 계획/버튼/현재·과거 결과, SaveAs·최근 복구·구버전 호환.
6. 독립 검토/전체 회귀/문서·버전·EXE 검증.

필수 테스트: 각 단계 시작 전/도중/게시 직후/완료 저장 실패의 중단, main DONE 이후 output 오류, 성공 파일 유지 및 변경/누락 차단, SKIPPED/SIZE_EXCLUDED 유지, move 원본 보존·제거 전후 중단, JSON/DB 손상·저장 실패, 오래된 READY 사본·SaveAs·다른 폴더 복구, 동시 실행, 링크/경로 이탈/외부 경합, 새 파일명·모델 선택·SEQ·촬영 날짜 유지. 10만 항목에서 전체 JSON의 단계별 재저장 없이 동작하는지도 검증한다.

## 8. 독립 판단 취합

엔진/저장/UI 세 관점의 판단을 취합했다. 공통 권고는 단계 기록, 기존 성공 유지, 불확실 항목 보존·차단, 구형 ERROR 자동 재해석 금지다. 저널은 JSONL 또는 SQLite 의견이 나뉘었다. 트랜잭션·고유 plan 등록·이력 조회를 표준 라이브러리로 제공하는 SQLite를 선택했다. UI는 이어하기와 실패 재시도를 구분한다. 사용자 승인 후 구현 계획과 검증을 완료했다.
